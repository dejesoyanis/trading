## Cross-decision consistency

These readings bind the fourteen choices together. They do not add a fifteenth choice. They do not supersede ARCH-DEC-03, ARCH-DEC-04, ARCH-DEC-07, ARCH-DEC-13, ARCH-DEC-14, ARCH-DEC-17, ARCH-DEC-26, ARCH-DEC-33, ARCH-DEC-34, or ARCH-DEC-35 through ARCH-DEC-48.

- **IBKREVQ-01 B accepts only obtained primary text.** A later citation needs a versioned official IBKR primary text that was actually retrieved, with a retrieval date, and a second independently retrieved copy of that same version before E4 may cite it. The second copy is not an independent empirical broker confirmation. No source, URL, version, or procurement is invented here. This choice does not start E0.
- **IBKREVQ-02 A pins one tuple per future package.** A future evidence package names one product, API client, platform, operating system, and account-mode tuple, plus the environment facts that package actually has. Another tuple needs another package. No version value is invented. No result transfers to every tuple.
- **IBKREVQ-03 A records only supplied scope.** Account, client, session, dataset, time window, and environment are written down only when the request or the payload actually carries them. A missing field stays missing. There is no global snapshot and no coverage proof.
- **IBKREVQ-04 B leaves the environment class open.** Paper, sandbox, and every other environment label stay unchosen until official E0 documentation uses the broker's own words, and a later decision names the class. This choice does not approve a test environment or an account.
- **IBKREVQ-05 B forbids a broker read until a later named-operation decision.** No connection and no read happen before a separate dated decision names the exact officially documented read operations that would be allowed. This ratification names no operation and does not authorize E2. Cancel, modify, and replace are never declared to be reads.
- **IBKREVQ-06 B separates capture completeness from broker completeness.** A future oracle note records scope, stored bytes, and local gaps, and states that capture completeness is not broker completeness and that broker completeness was not shown. Coverage stays `UNKNOWN`. No completeness token is stored. An empty response is not a negative proof.
- **IBKREVQ-07 A allows a later reuse observation inside one pinned tuple.** A later controlled examination may report whether `orderId`, `permId`, or `execId` was reused inside that one tuple. The report is an observation. It is not a uniqueness guarantee, not a UNIQUE index, and not an automatic economic assignment. No such test is authorized today.
- **IBKREVQ-08 A links a correction only when the new raw payload names it.** A structured correction or bust reference is kept only when the new raw payload itself contains the reference. Original bytes stay append-only. No invented link, no reversal booking, no risk release, and no closure change are approved.
- **IBKREVQ-09 B keeps unknown-send cases synthetic and offline.** Until a new explicit decision, crash and disconnect cases for an unknown send are synthetic or offline only. No fault injection against a broker, no E3 authorization, no retry, no resend, and no takeover are approved.
- **IBKREVQ-10 A is a checklist and not a takeover proof.** A future writer-isolation package must show, separately, process-stop and connection-closed artifacts, or a credible session-exclusivity confirmation, together with reconciliation of unknown attempts. `WriterEpoch` and the lease deadline stay separate facts. The checklist is not sufficient proof of takeover and not an operational approval path. CR-B01 stays ahead of a weaker DET-07 reading.
- **IBKREVQ-11 A keeps future raw payloads outside Git.** A later store, if a later decision creates one, keeps raw payloads immutable, append-only, and secret-protected outside this Git repository, with hashes, the version tuple, and redacted logs. Contradictory original bytes are kept. This ratification creates neither the store nor a payload, and it puts no secret in Git. Location, access control, and retention remain for a later approval.
- **IBKREVQ-12 A refuses automatic transfer to a new tuple.** A change of product, API client, platform, operating system, or account mode means earlier external claims do not apply to the new tuple. A new package and a new decision are required. No calendar period is invented. No universal statement is made.
- **IBKREVQ-13 A stops the later stage on unexpected behavior.** The later stage stops. An escalation marker may be recorded for a human. The marker is not a role and grants no reset, post, release, or dispatch right. If a required second approval is missing, the result is deny. This choice does not start a stage.
- **IBKREVQ-14 B separates capture from ratification.** Future collection and future acceptance use different instructions and different Git commits. A review note inside a capture package is not a decision. Only a later dated user decision, after the artifacts exist, can accept named evidence. That later decision would still not authorize implementation or live trading.

A passing documentation test and `external_broker_tests_executed=false` are different facts. The first can be true for repository rules. `external_broker_tests_executed` stays false. Neither fact is broker evidence.
